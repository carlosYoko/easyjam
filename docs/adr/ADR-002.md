# ADR-002 — Biblioteca persistente y preparación musical previa

- **Estado:** aceptado como dirección arquitectónica inicial por D013, revisable mediante evidencia. Vue 3/TypeScript, backend local mínimo, SQLite, módulos/adaptadores sustituibles, trabajos durables y original/arreglo separados aprobados. El esquema de siete tablas NO es obligatorio; usar el modelo más sencillo que cumpla invariantes y pruebas. Driver/framework, motor, serialización y alphaTab siguen sujetos a evaluación. Solo formalización y planificación S06 autorizadas; no código todavía.
- **Fecha:** 18 de octubre de 2026.
- **Ámbito:** M001 revisado; sustituye la dirección candidata de ADR-001, no las pruebas válidas de T01/T02.
- **Referencias:** [producto](../product.md), [roadmap aprobado](../mvp-proposal.md).

## 1. Dirección aceptada; detalles ajustables

Conservar Vue/Vite/TypeScript y el adaptador oficial existente. Añadir un único backend local Node/TypeScript, una base SQLite en directorio de datos estable y un ejecutor de trabajos persistidos, con concurrencia inicial uno. El analizador corre fuera del hilo HTTP mediante proceso hijo controlado o un proveedor permitido, según la prueba de viabilidad. Si el motor requiere Python, sería un ejecutable/adaptador, no un segundo backend HTTP ni un microservicio.

Nada de Redis, broker externo, cuentas, ORM obligatorio, nube, SSR o servicios distribuidos. No elegir framework HTTP, driver SQLite, motor o renderer hasta revisar compatibilidad/licencias y aprobar el plan. Evaluar primero opciones maduras y pequeñas compatibles con el Node fijado.

**Entorno propuesto:** aplicación local monousuario. Backend en loopback y misma procedencia para UI/API; fichero de datos fuera de dist, temporales y del directorio de trabajo variable. Sin autenticación de usuario no se autoriza exponerlo en red/Internet. Una futura distribución requiere otra revisión de seguridad y privacidad.

## 2. Límites y contratos candidatos

```text
Vue: Mi biblioteca / Añadir canción / Práctica
                 ↓ HTTP tipado + validación runtime
Casos de uso: AddSong, GetLibrary, GetPractice, RetryPreparation, RegenerateArrangement
                 ↓ contratos concretos
LibraryRepository | PreparationJobs | AuthorizedAudioSource | MusicAnalyzer
                                      ArrangementGenerator | SyncMapValidator
                 ↑ adaptadores
SQLite | metadatos YouTube | fuente licenciada | motor local/proveedor autorizado

Práctica → arreglo/sync guardados → PlayerPort existente → iframe oficial visible
```

Son nombres candidatos, no exports existentes. El dominio musical recibe datos validados y no importa Vue, SQL, HTTP, APIs YouTube ni el motor. Contratos de persistencia expresan operaciones transaccionales completas (`addOrGet`, `claim`, `saveTranscriptionCheckpoint`, `publishPracticeResult`), no una secuencia de CRUD que obligue a la aplicación a coordinar transacciones SQLite. No exponer conexiones SQL al dominio ni crear un repositorio universal.

El servicio de reproducción recibe arreglo y mapa temporal almacenados. GetPractice es de lectura: no invoca analizador, generador ni fuente de audio. RegenerateArrangement usa solo la transcripción guardada y una receta explícita/versionada. No generar al abrir por un cambio de versión de software.

## 3. Flujo y contrato HTTP mínimo propuesto

| Operación | Resultado |
|---|---|
| POST /api/songs {youtubeUrl} | Canonicaliza; devuelve canción lista existente, estado/trabajo existente, o crea pendiente una vez. 200 reutilizada, 202 pendiente; 400 URL inválida. |
| GET /api/songs | Lista simple con estado/fase, título, miniatura disponible y canPractice. Sin filtros/estadísticas. |
| GET /api/songs/:id | Metadatos y estado persistido/proyectado, motivo y retryAllowed; no secretos. |
| GET /api/songs/:id/practice | Transcripción de referencia, arreglo y sync válidos. 409 si no preparado; fallo de YouTube no borra música. |
| POST /api/songs/:id/retry | Acción explícita, acotada y atómica; devuelve trabajo activo si existe. No reinicia resultados completos. |
| POST /api/songs/:id/arrangements | Regenera con receta aprobada desde transcripción aceptada; reutiliza receta existente. UI mínima, no editor avanzado. |

Errores con código estable, fase y mensaje seguro. Persistencia interna candidata: `pending`, `processing`, `ready`, `error`, con phase validada (resolving_source, awaiting_authorized_source, analyzing, validating, arranging, aligning). La UI proyecta exactamente **Pendiente / Analizando / Preparando arreglo / Lista / Error**: pending y resolución/validación inicial del material (aún sin análisis musical) → Pendiente; processing+analyzing/validating → Analizando; processing+arranging/aligning → Preparando arreglo; resultado válido completo → Lista; fallo sin resultado válido → Error. La fase precisa aparece como explicación, no estados inventados. Separar validación inicial de material y validación musical. `pending + awaiting_authorized_source` explica el bloqueo; no simula trabajo ni extrae YouTube. No añadir subida de archivos sin aprobar el cambio.

POST confirma el trabajo guardado y termina sin esperar al motor. Un ejecutor administrado por backend, no la petición HTTP ni Vue, procesa la cola durable. Desconexión HTTP, desmontaje, recarga, cierre del navegador o ausencia de polling NO cancelan el trabajo. Al volver se lee el estado de SQLite; polling solo observa. Si backend/equipo se apagan, el cálculo se detiene o interrumpe según ejecutor y debe reconciliarse desde checkpoint al reiniciar; independencia del navegador no significa cómputo sin proceso activo. Sin colas externas/microservicios.

Canonicalizar sin fetch arbitrario: HTTPS, hosts exactos permitidos, watch?v, youtu.be, shorts/embed soportados explícitamente, ID de 11 caracteres [A-Za-z0-9_-], sensible a mayúsculas. Descartar t/list/tracking de la identidad; rechazar múltiples IDs incompatibles, URLs con credenciales, esquemas/puertos/hosts no admitidos y playlists sin vídeo. Confirmar existencia/insertabilidad mediante la API documentada, no mediante redirecciones o scraping. Una canción guardada puede abrir su arreglo aunque una actualización de metadatos falle.

## 4. Modelo lógico mínimo propuesto

Siete tablas como ejemplo de descomposición, **no mínimo obligatorio** (D013). S08 debe elegir el menor esquema suficiente y justificar separación o combinación por constraints/transacciones/retención/migración; JSON versionado puede bastar para detalles musicales y anclas. No imponer un repositorio por tabla, lease distribuida o framework de jobs. Las invariantes de identidad, original/arreglo separados, checkpoints y publicación segura sí son requisitos, cualquiera que sea el número de tablas. Las migraciones son infraestructura; UUID/entero y driver se decidirán al implementar. JSON musical versionado evita una fila SQL por nota sin impedir validación estricta o migración. Ningún BLOB de vídeo/audio YouTube.

| Tabla | Campos mínimos / relaciones / invariantes |
|---|---|
| songs | id PK, youtube_video_id NOT NULL UNIQUE con comparación binaria, created_at, updated_at. Identidad extraída de entrada del usuario; no texto completo de URL ni cookies. |
| youtube_metadata | song_id PK/FK, title, thumbnail_url nullable, duration_seconds nullable, embeddable/made_for_kids nullable, fetched_at, expires_at. Caché de datos API separada, refrescable/borrable. Placeholder por ID cuando falte; no inferir madeForKids. |
| audio_sources | id PK, song_id FK, origin/provider_asset_id no secreto, checksum del archivo verificado, recording_identity, permission_reference/scope, verified_at, availability/retention info. Referencia a recurso permitido; enlaces firmados/credenciales se resuelven fuera de DB/logs. |
| transcriptions | id PK, audio_source_id FK, input_checksum, engine/model_version, config_hash, schema_version, musical_payload_json, audio_timing_json, quality/warnings, acceptance_status, created_at. UNIQUE(audio_source_id, input_checksum, engine_version, config_hash, schema_version). Original inmutable del análisis, no arreglo. |
| arrangements | id PK, transcription_id FK, recipe_hash/version, schema_version, tuning/range/difficulty, musical_payload_json, validation_status, created_at. UNIQUE(transcription_id, recipe_hash). Receta incluye política armónica/rítmica, afinación, trastes y versión del optimizador. No sobrescribir versiones válidas. |
| sync_maps | id PK, transcription_id FK, youtube_video_id, revision, schema_version, mapping_json, acceptance_status, validated_at. UNIQUE(transcription_id, youtube_video_id, revision). Alineación para grabación concreta; no repetir analysis para cambiar un desfase. |
| preparation_jobs | id PK, song_id FK, kind (prepare/arrange), request_key, transcription_id nullable FK, state, phase, attempt, run_token, started_at, heartbeat_at, finished_at, error_code, safe_error_detail, retryable, created_at. UNIQUE(song_id, kind, request_key); índice parcial único de trabajo activo por song_id. |

Constraints SQL: FK activas en cada conexión, NOT NULL, CHECK de enums/contadores/JSON válido y límites básicos. Validación musical runtime: orden/no solapamiento permitido por modelo, referencias, cobertura de secciones, tempo positivo/unidades explícitas, silencios, duración finita, símbolos ambiguos y mapa monótono. Validación de publicación comprueba que transcripción, arreglo y sync pertenecen a la misma canción/versión/grabación. La validez sintáctica JSON no acredita estas reglas.

**Estado de canción como proyección**, no segundo estado mutable independiente: lista si hay transcripción aceptada + arreglo válido + sync aceptado compatible; de lo contrario según trabajo pendiente/procesando/error. Una regeneración fallida no quita la disponibilidad del último arreglo válido; se muestra el fallo del trabajo aparte. `canPractice` no se deduce solo del estado exitoso del analizador.

Metadatos: antes de servir una caché expirada, refrescarla o suprimir los campos API vencidos según política aplicable (III.E.4, máximo general 30 días para datos no autorizados). Refresco fallido no destruye resultados musicales independientes ni los vuelve a analizar. No descargar miniaturas como blobs por comodidad; revisar condiciones de presentación, solicitudes externas y borrado. La política de datos API no sustituye la de fuentes/transcripciones independientes autorizadas.

## 5. Atomicidad, exclusión y reintentos

Índice lógico candidato (documentación, no migración implementada):

```sql
CREATE UNIQUE INDEX one_active_preparation_per_song
ON preparation_jobs(song_id)
WHERE state IN ('pending', 'processing');
```

1. AddSong: transacción corta BEGIN IMMEDIATE; INSERT canción ON CONFLICT(youtube_video_id) DO NOTHING; leer identidad/resultados; devolver cache válida/trabajo activo o insertar trabajo idempotente. Commit. No `SELECT si no existe → INSERT` sin protección, ni INSERT OR REPLACE que borre relaciones.
2. Claim: transición condicional pending→processing y nuevo run_token en transacción; solo una conexión gana. Trabajos awaiting_authorized_source no se reclaman repetidamente. Resolver audio únicamente con adaptador autorizado, allowlist y procedencia conocida, nunca con la URL arbitraria del usuario.
3. Audio/modelo/HTTP fuera de transacciones SQL. **Calidad antes que velocidad:** aceptar procesamiento igual o bastante mayor que duración; no deadline musical ni límite arbitrario de ratio. Medir hardware/tiempo/memoria/coste, justificar límites operativos y distinguir timeout de red, heartbeat de ejecutor, progreso real de fase y detección de cuelgue. Un motor computando puede no emitir nuevos eventos musicales; falta de porcentaje no acredita cuelgue ni autoriza otro ejecutor. Guardar fase/checkpoints/versión; sin porcentaje/ETA inventados. Proceso hijo sin shell y argumentos controlados; salidas no confiables validadas.
4. Tras análisis aceptado, checkpoint transaccional: guardar original inmutable y referencias/avance del trabajo, verificando run_token. Si después falla el arreglo/sync, reintentar esa fase sin repetir el audio ya analizado.
5. Publicación final: validar todo y persistir arreglo/sync aceptado + éxito del trabajo atómicamente con el mismo fencing token. No publicar ready a medias; ninguna respuesta de un ejecutor obsoleto puede sobrescribirla.
6. SQLITE_BUSY: espera/reintento de operación SQL corto y acotado; si se agota, error recuperable seguro. Jamás reintentar todo el análisis por una contención de escritura. I/O/disco lleno provoca rollback comprobado, no una canción falsamente lista.
7. Reinicio: pending ejecutable se conserva; processing interrumpido se reconcilia solo al confirmar que el ejecutor anterior terminó/canceló. Error persistido con fase/intento; reintento explícito, límite y no duplicación. Heartbeat/lease indica sospecha, no permiso suficiente para ejecutar dos análisis a la vez.
8. Un timeout remoto con resultado desconocido no se reenvía ciegamente: consultar job ID/idempotency key si el proveedor lo permite; en caso contrario error de resultado incierto y decisión controlada. Garantía: una publicación lógica y exclusión de trabajos; no prometer exactamente-una-ejecución física frente a cualquier crash/proveedor.

Guardar SQLite en fichero/volumen estable con migraciones versionadas. Elegir journal/timeout y estrategia de copia coherente de SQLite tras pruebas; WAL no equivale a múltiples escritores ni justifica copiar solo el fichero principal mientras esté activo. No crear DB/migraciones durante esta propuesta.

## 6. Tiempo y contenido musical

Transcripción: armonía reconocida, eventos/duraciones, beats/compases, secciones inferidas, silencios y advertencias; audio_timing enlaza música con segundos del audio autorizado. SyncMap relaciona esa referencia con el vídeo concreto. Un offset no basta para una edición con cortes, introducción distinta o cambio de velocidad: validar anclas monótonas/segmentos y rechazar correspondencia insegura.

Arreglo: conserva ritmo/silencios y secciones, transforma armonía compatible a quintas, escoge digitaciones globalmente y almacena las posiciones. Patrones simplificados derivados se identifican como decisiones del arreglo, no como rasgueos detectados fielmente. N.C. de un detector de acordes no prueba silencio de guitarra. El modelo debe conservar desconocido/revisión, no inventar silencio o fundamental.

Durante práctica se reutilizan PlayerPort/YouTube adapter y reglas [inicio,fin) de T02 como evidencia/patrón, no TechnicalGuide como modelo final. **Pentagrama y TAB son obligatorios y representan el mismo arreglo simplificado**, no el original complejo. alphaTab es el primer candidato, no una adopción; no escribir renderer propio sin demostrar que bibliotecas maduras son insuficientes y obtener decisión.

### 6.1 Modelo notacional candidato (no esquema implementado)

El arreglo necesita algo más que nombres de acordes y ventanas de segundos. Proponer e investigar:

- Identidad/versiones, referencia a original y receta, afinación y orden inequívoco de cuerdas; posiciones de dedo ya elegidas globalmente.
- Eje musical exacto en ticks con PPQ explícito/versionado o racionales: elegir después de probar tuplets/duraciones, no fijar 960 por copiar un ejemplo. Segundos de audio/vídeo aparte.
- Compases con índice/número, métrica y duración; anacrusa si existe, eventos que cruzan barra ligados, tempo/cambios cuando los haya, secciones referidas a posiciones musicales.
- Eventos con inicio/duración, nota o quinta simultánea (fundamental+quinta), altura/octava sonora y escrita con transposición de guitarra explícita, cuerda/traste, silencios explícitos. Si la canción lo requiere, puntillos/ligaduras/subdivisiones/tuplets. Sin exigir todas las articulaciones/instrumentos futuros.
- Pentagrama y TAB consistentes: misma nota/duración, afinación/rango, total por compás coherente, ties sin reataque, rest distinto de desconocido. Orden MIDI grave→aguda frente a numeración alphaTab debe adaptarse/probarse.
- Repeticiones: fijar secuencia de reproducción y ocurrencia de compás; una barra repetida no tiene necesariamente una sola posición multimedia. Evaluar desplegar compases para simplificar MVP en vez de implementar saltos musicales complejos sin necesidad.
- Anclas monotónicas de posición musical/ocurrencia a tiempo externo observado, identidad/revisión de grabación, incertidumbre/validación. Una corrección de anclas no altera original ni invoca analizador.

Guardar modelo neutral validado/versionado en arrangements, no objetos internos alphaTab como única fuente. Adaptador Score/alphaTex/Guitar Pro por evaluar; elegir ruta mínima que preserve ligaduras, duración, alturas, cuerdas/trastes y sync sin pérdidas. No asumir que MIDI de un detector contiene compases, digitaciones o silencios de guitarra correctos. No parsear/renderizar SQL en componentes.

### 6.2 Evaluación prioritaria alphaTab y sincronización

Documentación consultada con Context7 `/websites/alphatab_net`: Staff permite showStandardNotation/showTablature; player dispone de cursor, scrollMode/scrollElement e interacción de seek; guía Audio & Video Sync documenta EnabledExternalMedia, IExternalMediaHandler, updatePosition y sync points con compás/ocurrencia/posición. Son capacidades documentadas, **no integración EasyJam probada**. Los snippets con APIs HTTP o variables inconsistentes no se adoptan; verificar referencias/tipos/versión reales al prototipar.

Prueba temprana propuesta S07 antes del backend completo:

1. Convertir un arreglo piloto legítimo/revisado a pentagrama+TAB simultáneos; comprobar compases/duraciones/rests/ligaduras/notas/quintas/cuerdas/trastes. Identificar piloto y límites; no atribuir una fixture al audio como transcripción real.
2. Mantener PlayerPort como autoridad. Adaptador renderer/sync convierte segundos↔milisegundos y posición musical; no duplicar handlers globales de YouTube o crear segundo player/sintetizador audible.
3. Alimentar updatePosition desde observaciones y anclas; cualquier interpolación/animación interna de alphaTab debe congelarse en pausa/buffering y reconciliarse tras seek. No aceptar el ejemplo de polling 50 ms como precisión o solución de buffering. Probar eventos externos y seek iniciado en partitura sin bucles de callbacks ni movimiento optimista.
4. Usar cursor/scroll nativos. Visor principal, panel YouTube lateral/superior no ocultado por scroll/overlays y tamaño mínimo preservado. Seleccionar compás/sección solicita seek; sección actual por posición observada, teclado y foco no secuestrados por scroll.
5. Persistir/reabrir anclas corregidas; verificar unidades, ocurrencias, offset y varias anclas, pausa/fin y grabación incompatible. Mecánica mínima de ajuste por aprobar; no editor completo implícito.
6. Comprobar licencia/dependencias/assets, bundle, Vue/TS, CSP/workers si necesita, accesibilidad y limpieza. Si no cubre el contrato, presentar alternativa madura/impacto antes de cambiar experiencia o construir renderer.

### 6.3 Evaluación del análisis orientada a calidad

Comparar línea base reproducible sobre audio autorizado con armonía/cambios, notas relevantes de la parte rítmica, beats/downbeats/métrica/duraciones, silencios/secciones y alineación revisados. Candidatos iniciales: Chordino/NNLS Chroma, herramientas QM Vamp y Basic Pitch (limitación documentada de instrumento individual); no equivalen a solución integrada ni a elección de motor.

Proponer experimentos de normalización/remuestreo compatibles, separación armónico/percusiva, separación de fuentes con herramienta existente o análisis de contexto/varias pasadas solo con hipótesis medible. No normalizar/cuantizar borrando silencios, dinámica útil o microtiempo; conservar mapeo y versión de cada transformación y sus latencias. Comparar baseline vs cambio de una técnica con misma referencia/hardware/semilla/configuración; registrar mejora y degradaciones por dimensión más tiempo/recursos. Separación de fuentes puede añadir artefactos: no se presupone mejora. No implementar separador propio ni adoptar más dependencias sin evidencia/licencia.

Umbrales numéricos y workflow de corrección se acuerdan después de medir, antes de go/no-go. El objetivo es rítmica simplificada tocable y alineada, no transcripción exacta de toda la polifonía. Error/no disponible no se convierte en música ficticia ni en resultado listo.

## 7. Seguridad y operación mínimas

- Servir loopback/same-origin, validar Host/Origin y bloquear escrituras cross-origin; no confiar en CORS como autenticación. Sin backend público sin nueva decisión.
- Consultas parametrizadas, esquemas de entrada, límites de carga/trabajo y un solo ejecutor; sin rutas/órdenes arbitrarias desde URLs.
- Claves solo en configuración segura del servidor. Ficheros temporales autorizados con política de borrado en éxito/error/cancelación; conservar audio solo si el permiso/retención lo permiten y es necesario. Checksums/procedencia no son permiso.
- Diagnóstico mínimo persistente: job ID, estado/fase/intento, fechas, error seguro y versiones; sin cookies/tokens/URLs firmadas o audio en logs.
- Status/health interno distingue backend, acceso a DB y ejecutor; no una plataforma de observabilidad ni datos personales.

## 8. Alternativas y decisiones pendientes

- Solo navegador/IndexedDB: no cumple por sí solo SQLite de servidor y ejecución segura propuesta; descartado como sustitución silenciosa.
- SQLite WASM/OPFS: posible alternativa técnica, pero añade consideraciones de persistencia/cuotas/compatibilidad y ejecución del analizador. No adoptada frente al backend mínimo solicitado.
- PostgreSQL/cloud/colas: sin requisito actual; SQLite cubre un usuario y la serialización necesaria.
- Fuente licenciada resuelta por ID: mejor conserva URL sola, pero requiere un proveedor/mapping real, permisos, cobertura y posibles costes; ninguno contratado/probado.
- Archivo propio + URL: **autorizado para la prueba S06 por D013**, con procedencia/permiso y correspondencia revisadas. No supone aprobar subida de archivos en el producto, ni acreditar URL única o cambiar el MVP. Si no hay resolutor permitido, el informe mantiene ese requisito abierto y presenta alternativas/impacto.
- Partitura importada: permite practicar/persistir pero NO demuestra generación real; no sustituye el MVP sin redefinición explícita.

**Autorización actual (D013):** dirección inicial y roadmap S06–S11 aceptados, con KISS/SOLID/YAGNI y esquema simplificable. Solo se formaliza y planifica S06; sus tareas se revisan antes de ejecutar código, una unidad explícita cada vez. No autoriza S07–S11, auto, cierre, merge o push. No elegir motor, prometer URLs arbitrarias o dar por demostrada integración/SQLite/worker por aprobación documental.
