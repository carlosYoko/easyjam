# ADR-001 — Arquitectura inicial de EasyJam

- **Estado:** propuesta (pendiente de aceptación)
- **Fecha:** 18 de octubre de 2026
- **Responsables:** equipo EasyJam (por asignar)
- **Ámbito:** frontend, modelo musical, dependencias, integración multimedia y estrategia de evolución
- **Documentos relacionados:** [constitución](../constitution.md), [producto](../product.md)

## 1. Contexto

EasyJam debe ofrecer una primera experiencia **individual**: mostrar la estructura de una canción, reproducirla mediante un vídeo de YouTube integrado y presentar un arreglo rítmico simplificado en quintas con digitaciones cómodas. En el futuro se prevén varias pistas (rítmica, solista, bajo), diferentes dificultades y generación de arreglos desde fuentes autorizadas.

Riesgos principales: complejidad musical innecesaria, acoplamiento con un framework full-stack, representación temporal insuficiente para varios instrumentos, latencia de sincronización y licencias/restricciones del contenido.

No hay requisitos demostrados de renderizado en servidor, autenticación, backend de procesamiento musical ni colaboración en tiempo real para el MVP.

## 2. Decisión

Adoptar una **SPA con Vue 3 + Vite + TypeScript**, organizada como **monolito frontend modular**, con **Clean Architecture / Hexagonal ligera** solo en límites que aporten aislamiento comprobable:

1. **Dominio:** modelos y reglas musicales sin dependencias de framework.
2. **Aplicación:** casos de uso que operan sobre el dominio y puertos explícitos.
3. **Infraestructura:** adaptadores a YouTube, teoría musical, tablaturas y almacenamiento opcional.
4. **Presentación:** componentes Vue y módulos por funcionalidad.

**No implementar backend al inicio.** Incorporarlo únicamente para una función que lo requiera (p. ej., análisis de audio autorizado, biblioteca compartida o tareas pesadas).

Decisiones de dependencias:

- **Vue 3 / Vite / TypeScript (strict):** propuestos como base, pendientes de aprobación.
- **Pinia:** introducir solo si el estado de práctica debe compartirse entre funcionalidades; evitar trasladar las reglas musicales al store.
- **Vue Router:** solo si hay varias rutas útiles; no forzar routing para una única pantalla de prototipo.
- **Tonal.js:** candidato para teoría musical, accesible detrás de un adaptador; validar compatibilidad con los símbolos soportados.
- **alphaTab:** candidato para renderizado de tablaturas, sujeto a un *spike* de sincronización y facilidad de generación de partituras desde nuestro modelo.
- **YouTube IFrame Player API:** proveedor para reproducción embebida visible, sin descargar ni aislar audio.
- **Vitest + Vue Test Utils + Playwright:** herramientas de pruebas propuestas.

**Patrones usados por necesidad:** ports/adapters en integraciones externas; Strategy como funciones intercambiables para la selección de digitaciones; Repository cuando exista almacenamiento; máquina de estados simple para la sesión de reproducción. **No** CQRS, Event Sourcing ni microservicios.

## 3. Vista lógica y dirección de dependencias

```text
                    PRESENTACIÓN
            Vue / componentes / features
                           |
                           v
                    APLICACIÓN
           Use cases / puertos / DTOs
                           |
                           v
                       DOMINIO
       Song, Arrangement, Track, Event,
       Timing, Chord, Fingering, Optimizer
                           ^
                           |
                    INFRAESTRUCTURA
   YouTube adapter | Tonal adapter | Tab adapter
                 | Storage adapter
```

Las flechas representan dependencias de código hacia el núcleo, **no** el flujo de ejecución. Un caso de uso puede invocar un puerto implementado por infraestructura mediante inyección explícita.

Reglas de dependencia:

- `domain` no importa nada de `application`, `features` o `infrastructure`.
- `application` no importa Vue, APIs de proveedor ni módulos de UI.
- `features` depende de `application`/tipos de dominio; la UI no decide digitaciones.
- `infrastructure` implementa los contratos de `application` y adapta formatos ajenos.
- Los módulos internos se comunican mediante exportaciones públicas, no rutas profundas a implementaciones de otros módulos.

## 4. Modelo musical inicial

Se reserva un eje temporal musical compartido para todas las pistas, incluso cuando el MVP solo renderice una. Usar un contador **entero de ticks musicales** (por ejemplo `PPQ = 960` ticks por negra) evita redondeos acumulados por duraciones fraccionarias. El mapa de tempo convierte ticks a tiempo de canción; los puntos de sincronización alinean tiempo musical y segundos de una fuente concreta.

```ts
// Boceto de contrato de dominio, NO API definitiva.
type MusicalTick = number; // entero >= 0, PPQ conocido y versionado

type Instrument = "guitar" | "bass";
type TrackRole = "rhythm" | "lead" | "bass";

type MusicalEvent =
  | {
      kind: "chord";
      startTick: MusicalTick;
      durationTicks: number;
      chordSymbol: string;
    }
  | {
      kind: "note";
      startTick: MusicalTick;
      durationTicks: number;
      midiNote: number;
    }
  | {
      kind: "rest";
      startTick: MusicalTick;
      durationTicks: number;
    };

interface Track {
  id: string;
  instrument: Instrument;
  role: TrackRole;
  tuningMidi: readonly number[]; // orden definido: grave -> aguda
  events: readonly MusicalEvent[];
}

interface Section {
  id: string;
  name: string;
  startTick: MusicalTick;
  endTick: MusicalTick; // intervalo [inicio, fin)
}

interface TempoChange {
  tick: MusicalTick;
  bpm: number; // valor positivo
}

interface SyncAnchor {
  tick: MusicalTick;
  mediaSeconds: number;
}

interface Arrangement {
  schemaVersion: 1;
  id: string;
  songId: string;
  revision: number;
  difficulty: "easy" | "intermediate" | "advanced";
  sections: readonly Section[];
  tracks: readonly Track[];
  tempoMap: readonly TempoChange[];
  syncAnchors: readonly SyncAnchor[];
}
```

**Notas de diseño:**

- `Song` representa identidad/metadatos; `Arrangement` representa una versión interpretable con dificultad y procedencia; `Track` representa un instrumento/función; `Section` delimita partes temporales, y los eventos sonoros o silencios pertenecen a pistas.
- El arreglo no contiene la URL incrustada como dependencia estructural de YouTube. La asociación canción ↔ fuente externa se gestiona mediante referencias y metadatos de reproducción.
- La primera iteración puede limitar el tempo a una única entrada, pero el esquema permite cambios posteriores.
- Los `SyncAnchor` constituyen una hipótesis de alineación editable, **no una garantía** de sincronía absoluta. Comprobar si dos o más anclas son necesarias con casos reales.
- Afinaciones y notas MIDI internas deben definir de forma inequívoca orden de cuerdas, octavas y transposición.
- Se requieren validaciones de contratos en el límite de entrada (p. ej., Zod u otro validador si hace falta); no confiar únicamente en tipado en compilación.

## 5. Simplificación y optimización

El pipeline pertenece a casos de uso puros o servicios de dominio independientes:

```text
Progresión temporizada -> normalización de símbolos
                       -> extracción de fundamental
                       -> conversión a quintas
                       -> posiciones válidas por afinación
                       -> optimización global
                       -> eventos renderizables de tablatura
```

**Transformación:** para acordes mayores/menores regulares se conserva la fundamental y se sustituye su contenido armónico por fundamental + quinta justa. Acordes slash, aumentados, disminuidos o ambiguos no deben convertirse sin una política explícita y trazable.

**Generación:** obtener todas las posiciones útiles en el rango configurado, incluyendo alternativas en cuerdas contiguas y disposiciones de dos/tres notas cuando se soporten. No introducir notas que no pertenezcan a la quinta prevista.

**Selección:** el coste combina desplazamiento de mano, cambio de cuerdas, apertura incómoda y penalización de posiciones extremas, con pesos configurables. Para una secuencia de candidatos puede emplearse **programación dinámica**:

```text
C_i(p) = costeLocal(p)
       + min_q [ C_(i-1)(q) + costeTransición(q, p) ]
```

Esto permite minimizar coste en la **canción completa**, en vez de escoger cada acorde por cercanía inmediata. El modelo concreto de coste y sus pesos son hipótesis a validar con guitarristas.

El renderizador no debe alterar las decisiones musicales del optimizador: solo representa eventos y posiciones ya decididos.

## 6. Reproductor y sincronización

Un puerto de aplicación desacopla la sesión de práctica del proveedor:

```ts
interface PlayerSnapshot {
  seconds: number;
  durationSeconds?: number;
  state: "idle" | "loading" | "playing" | "paused" | "ended" | "error";
}

interface PlayerPort {
  load(sourceId: string): Promise<void>;
  play(): Promise<void>;
  pause(): Promise<void>;
  seekTo(seconds: number): Promise<void>;
  snapshot(): PlayerSnapshot;
  subscribe(callback: (value: PlayerSnapshot) => void): () => void;
}
```

Para YouTube se implementa `YouTubePlayerAdapter` con la IFrame API. El flujo de sincronía toma el tiempo actual del vídeo, lo mapea a ticks musicales con tempo/anclas, determina el evento activo y publica un estado de vista inmutable. No se usará el tiempo transcurrido de la UI como fuente autoritativa tras pausas o búsquedas.

**Prueba técnica obligatoria (*spike*) antes de fijar el renderizador:**

1. Integrar un vídeo embebible y una tablatura de prueba con varios compases.
2. Comprobar play/pause/seek/cambio de sección y errores de vídeo.
3. Medir retraso percibido y divergencia de resaltado en navegadores de escritorio y móvil.
4. Valorar si alphaTab `IExternalMediaHandler` y su frecuencia de actualizaciones funcionan bien con el reloj accesible del iframe.
5. Elegir alphaTab o un visualizador de tablatura simplificado según el resultado; documentarlo en un ADR nuevo o actualización.

El reproductor de YouTube debe permanecer visible, respetar su tamaño/control y políticas vigentes. No se extrae, descarga, separa ni analiza audio alojado allí. El análisis automático futuro operará **únicamente** sobre entradas autorizadas y se diseñará como subsistema distinto.

## 8. Estrategia de pruebas y puertas de calidad

- **Unitarias (Vitest):** transformación a quintas, notas/tuning, enumeración de posiciones, coste y solución global, mapeo ticks↔segundos, silencios y secciones.
- **Contratos/adaptadores:** dobles de `PlayerPort`; parsing/validación de fixtures; estados de fallo del proveedor.
- **Componentes (Vue Test Utils):** selección de sección, foco, teclas, estados de vacío y cursor de tablatura.
- **End-to-end (Playwright):** recorrido completo con un reproductor falso determinista; prueba separada y no bloqueante con YouTube real si se puede automatizar con fiabilidad.
- **CI mínimo:** instalación reproducible + TypeScript strict + lint + test unitario + compilación. E2E en merge o release según tiempo de ejecución.
- **Accesibilidad:** navegación por teclado, lector de pantalla razonable, selección no basada solo en color.

**Pruebas de aceptación de ejemplo:** `C→C5`, `Am→A5`, posiciones alternativas G5/D5, progresión de cuatro acordes, afinación fuera de rango, orden temporal, seek y pausa; casos ambiguos marcados expresamente.

## 9. Alternativas analizadas

| Alternativa | Motivo para no adoptarla inicialmente | Reconsiderar si... |
|---|---|---|
| Next.js | Funciones SSR/full-stack y convenciones adicionales no aportan valor medido al MVP. | SEO por canción, SSR o backend integrado pasan a ser requisitos esenciales. |
| Nuxt | Mejor analogía con Next dentro de Vue, pero añade piezas que no necesitamos en la SPA inicial. | Se necesite renderizado híbrido/SSR real. |
| Backend Python/FastAPI desde el día uno | Crea operación y límites de red antes de necesitar análisis de audio. | Haya trabajos intensivos de audio desde archivos autorizados. |
| Microservicios | Coste de despliegue, observabilidad y consistencia innecesario. | Haya equipos, cargas o necesidades de escalado independientes verificadas. |
| Motor musical completo propio | Duplicaría teoría y renderizado existentes; mayor coste de mantenimiento. | Una librería crítica resulte insuficiente tras evaluación. |
| Tablatura exclusivamente propia | Menor dependencia, pero costaría reproducir funciones de notación maduras. | El spike revele que alphaTab es excesivo para la UI requerida. |

## 10. Consecuencias

### Positivas

- Menor acoplamiento a frameworks de servidor y proveedores multimedia.
- Motor musical testeable sin DOM, vídeo ni red.
- Capacidad de añadir instrumentos y dificultades sobre el mismo eje temporal.
- Entrega temprana de un recorrido vertical demostrable.

### Costes y límites

- Se deben mantener contratos y adaptadores pequeños, que implican cierto trabajo inicial.
- No hay generación automática de cualquier vídeo en el MVP: el contenido musical debe prepararse o suministrarse de forma autorizada.
- La sincronización con un proveedor externo no garantiza latencia estable; requiere medidas reales.
- Las heurísticas de comodidad pueden no coincidir con todos los guitarristas; requerirán validación y ajustes.
- Para un catálogo público, hay que resolver derechos de arreglos y licencias, no solo la embebibilidad de vídeos.

## 11. Criterios de revisión de este ADR

Revisar y registrar nuevo ADR si ocurre cualquiera de estas situaciones:

- El MVP necesita procesamiento de audio autorizado intensivo o almacenamiento compartido: evaluar backend/API.
- Hay requisitos medidos de SEO o renderizado en servidor: evaluar Nuxt.
- alphaTab no permite la UI/latencia requerida sin adaptaciones excesivas: cambiar adaptador/renderer.
- Se incorporan múltiples pistas o dispositivos y el modelo temporal actual demuestra limitaciones.
- Nuevas condiciones de licencia/plataforma impiden el enfoque de reproducción propuesto.

## 12. Siguientes pasos ejecutables

1. Ratificar `constitution.md` y confirmar alcance P0 de `product.md`.
2. Iniciar la discusión nativa con `/sdd discuss`, confirmar requisitos y propuesta de roadmap, y dejar que SDD Pi genere los artefactos de milestone, slices y tareas tras las aprobaciones correspondientes.
3. Hacer dos spikes acotados: **sincronía YouTube + tab** y **posiciones/algoritmo G5→D5**.
4. Elegir un arreglo de demostración con autorización documentada.
5. Construir la primera *vertical slice* con reloj simulado y pruebas antes de conectar el iframe real.
6. Revisar esta ADR con las conclusiones y cambiar su estado a **aceptada** cuando corresponda.
